Prepared 8 November 2026 (Asia/Karachi), from merged application `00fa9830e3444f35e8ed6a323fc2933a2d0e9970`. **This is a test plan, not evidence of hosted success.** All actual results below start Not verified. Do not overwrite another tester's records or interrupt their current session.

## 1. Agree the test window first

The founder and current tester must agree the exact host, deployed commit, Supabase project and reserved test records before anyone starts write tests. This document does not authorize migrations, account provisioning, institutional approvals or wallet transfers. No replacement hosted project is required or created by this task.

Testing lanes:

- **R — Read only:** existing public pages and already-consented synthetic records; no database changes. Public baseline pages do not require new migrations, but feature-specific R tests require the relevant schema below.
- **W — Application writes:** new labeled synthetic accounts/records and controlled updates through existing UI. No schema change, but founder authorization and compatible migrations are prerequisites. Do not use real qualifications or documents.
- **T — Blockchain:** separate explicit authorization; devnet only. Wallet ownership linking is W (message signing), not a transfer. Signing/broadcasting a proof/payment is T.

If a required column/view/RPC is missing, mark **Blocked**, stop that feature and ask the owner to complete the separately approved migration procedure. Do not run SQL fixes, weaken policies or keep retrying mutations.

## 2. Accounts and prerequisites

Use separate browser profiles:

- **C:** candidate, no organization/admin privileges.
- **O:** owner/reviewer of a clearly labeled test organization.
- **A:** existing platform administrator, independent of that organization.
- **X:** unrelated user, preferably belonging only to a different test organization.
- **P:** signed-out/Incognito visitor.

Never share passwords or reuse another person's session. The project owner, not the tester, must arrange any administrator bootstrap through the approved existing process. Do not let O approve itself. Never tick an identity/assessment review confirmation for work that was not actually performed, or impersonate a real institution for a test. If the approval cannot honestly be made, mark that scenario Blocked and obtain a legitimate reviewer/test arrangement; do not waive the gate. Do not make yourself an administrator by editing a profile. Existing membership roles determine which financial/owner actions are allowed; reviewers must not be assumed to have payment rights.

Before W/T tests: confirm the latest app schema. The current code expects all 19 migrations in the Task 17 readiness report. Tasks 14/15 specifically require `202611070002_organization_verification.sql` and `202611070003_assessment_transparency.sql`; Task 16 adds no migration. Contact, corrections, privacy and paid-work tests also require their earlier migrations. A recent filename alone does not prove it is outstanding.

Email confirmation and reset need actual delivery, correct Site URL and `/auth/callback` allowlisting (including recovery callback). No one should disable confirmation as a shortcut. Wallets need supported Phantom/Solflare extensions, or the respective mobile in-app browser; no desktop QR flow is promised.

### Wallet test safeguards

Use new dedicated test wallets with no mainnet funds, free devnet SOL and only tiny quantities of the configured test mint. Verify devnet genesis, token program and six decimals before T tests; selecting “devnet” in a wallet alone is insufficient. Record public signature, intent/attempt ID, time and expected test amount privately. Never provide seed/private keys. A payment outcome unknown after refresh must be reconciled from its original signature, not repaid. Signed browser storage can contain transaction references/bytes; do not clear site data before resolving attempts, or publish recovery exports.

Do not deliberately broadcast underpaid/wrong-mint transfers or replay transfers on the shared host. Those negative verification cases are already covered locally; arrange a separately approved controlled fixture if hosted testing is required. Mainnet funds, refunds and escrow are outside this plan.

## Completion and reporting

Record each scenario independently. Include public browser checks, authenticated journeys, negative API checks and real-wallet tests separately; a passing build is not a hosted pass. Stop the affected feature for privacy exposure, incorrect trust/validity, duplicate payment risk or schema mismatch; preserve signatures and report privately. Do not fix data or apply SQL yourself.

Founder sign-off should name: actual deployed SHA/project, completed migration evidence, test cases passed/failed/blocked, unresolved dependency risks, backup/recovery owner and authorized next step. Do not describe the pilot as production-ready or real-money-ready without this evidence and the appropriate security/legal review.
