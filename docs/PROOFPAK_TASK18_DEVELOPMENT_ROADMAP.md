# ProofPak Task 18 — Prioritized development roadmap

**Date:** 9 November 2026. Read with [the product audit](PROOFPAK_TASK18_PRODUCT_AUDIT.md). Source baseline: local `task-17-release-readiness` / `17b3dc8`, merged application `00fa983` and preserved Task 17 working files.

This document recommends work. It does not authorize implementation, database changes, backups, restoration, deployment or transactions. The current backup/migration work remains paused.

## Executive recommendation

**Next implementation task: keep a user's chosen opportunity through authentication.** A visitor should return to the challenge or paid project they intended to join after signing in, retrying an unsuccessful login, or completing account creation. Today paid-project login and signup lose that destination.

This is a focused repair to an existing core journey, not a new feature platform. It reuses Supabase Auth, the existing `next` field, the callback and safe-return validation. It can be implemented and tested locally without changing the hosted schema.

After that, improve Passport failure feedback, pending-action visibility and organization setup. Do not rebuild corrections, contact handoff, draft editing, cancellation, wallet ownership or transaction recovery: those already exist.

## Priority and impact rules

- **P0:** prevents reliable or safe core journeys/release. Includes operational blockers; these are recorded without resuming paused work.
- **P1:** makes the existing MVP understandable and useful end to end.
- **P2:** improves evidence quality, employer usefulness and operation of a controlled pilot.
- **P3:** valuable later, after repeatable hosted evidence.

Complexity: **Small** is a narrow change to existing screens/helpers; **Medium** spans a workflow and its tests; **Large** adds a material model, operating process or security boundary. These are relative estimates, not delivery-time promises.

Impact labels:

- **UI:** frontend/presentation only; no SQL or server permission change.
- **App:** frontend plus server routes/actions/query orchestration, reusing existing schema.
- **Schema:** a separately reviewed database change or activation of existing pending schema. Never hide this inside a UI task.
- **Operations:** configuration, release/testing or human process, separately authorized when needed.

## Recommended implementation order

1. **P1-01 authentication continuity**, locally, after approval. It helps a new visitor reach an existing core action immediately.
2. **P1-02 truthful Passport loading**, then P1-06 edit/publication clarity. Strengthen the professional record before adding more fields.
3. **P1-03 attention summary** and **P1-04 organization setup/context**, using existing full-schema local fixtures only until the hosted gap is resolved.
4. **P1-05 paid-work next steps**, preserving every payment lock and recovery reference.
5. Resume P0 operational gates **only when the owner separately chooses to unpause them**. Until then the new-schema hosted journeys remain blocked, regardless of local UX improvements.
6. Complete hosted two-party and device acceptance, refresh the dependency review, then choose P2 tasks from actual user feedback. Do not move directly to P3 because the repository contains many features.

## Definition of done for the next task

A new visitor can select one real-shaped opportunity, pass through the required authentication path and return to that same opportunity with an obvious permitted next action. Closed/unavailable work is handled truthfully.
